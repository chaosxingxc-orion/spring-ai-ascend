## 2. 本次新增/修复的关键进展

### 2.1 修复 call_versatile 在浏览器 ReAct 链路下参数丢失问题

问题表现：

```text
P8 单测成功，但浏览器 ReAct 链路中 call_versatile 返回：
{"error":"未知工作流类型","query":""}
```

定位过程：

- 模型生成的 `call_versatile` 参数正确；
- `VersatileInterruptRail` 发出的请求体却是：

```json
{"inputs":{"query":""},"stream":true}
```

根因：

```text
浏览器/ReAct 链路中，模型工具调用参数位于 ToolCall.arguments JSON 字符串；
原 Java Rail 只读取 inputs.getToolArgs()；
当 toolArgs 为空时没有从 ToolCall.arguments 兜底解析。
```

修复：

```text
VersatileInterruptRail 取参顺序调整为：
1. 优先读取 inputs.getToolArgs()
2. 如果为空，再读取 inputs.getToolCall().getArguments()
3. 如果 arguments 是 JSON 字符串，则解析成 Map
```

涉及文件：

- `agent-store/edp-agent-trae/spike/src/main/java/com/huawei/ascend/edp/rail/VersatileInterruptRail.java`

### 2.2 P8 测试改为覆盖真实 ReAct 参数形态

修改前：

```java
.toolArgs(Map.of(
    "query_description", "推荐理财产品",
    "query_intent", "理财推荐"))
```

修改后：

```java
.arguments("{\"query_description\":\"推荐理财产品\",\"query_intent\":\"理财推荐\"}")
.toolArgs(Map.of())
```

意义：

```text
P8 不再只覆盖手工构造 toolArgs 的理想场景，
而是覆盖浏览器/ReAct 真实链路中的 ToolCall.arguments JSON 字符串取参场景。
```

涉及文件：

- `agent-store/edp-agent-trae/spike/src/test/java/com/huawei/ascend/edp/spike/P8CallVersatileDirectSpikeTest.java`

## 3. 与 Python EDPA VersatileInterruptRail 的对比结论

当前 Java 版 `VersatileInterruptRail` 和 Python EDPA 的 `versatile_interrupt_rail.py` 不完全相同。

相同点：

```text
都支持工具参数归一化：dict/Map 与 JSON string 两种形态。
```

不同点：

| 对比项 | Python EDPA | Java 当前实现 |
|---|---|---|
| 调用模式 | interrupt + Orchestrator cascade resume | 直接 HTTP POST localhost:8095 |
| 首次 call_versatile | 记录 pending_delegate/pending_tool_context 后 interrupt | 直接调用 mock/Versatile REST 服务 |
| 是否直接调用外部工作流 | 否 | 是 |
| 是否依赖 Orchestrator | 是 | 否 |
| 是否有 cascade_result 恢复 | 是 | 当前没有 |
| 是否执行沙箱归一化脚本 | 是 | 当前直接解析 SSE/JSON 返回 |
| ToolDataChannel | 支持 input_key/result_key | 当前未接入完整通道 |
| todo_start/todo_end | 支持 | 当前未实现 |

当前 Java 实现符合本阶段已收敛的简化穿刺方向：

```text
EDPAgent call_versatile -> VersatileInterruptRail -> localhost:8095 REST service
```

也就是说，Java 当前是 P8 直连方案，不是 Python EDPA 的完整级联委托架构。
