## 1. 特性概述

- **特性描述**：

  本特性包含两个紧密关联的子能力：

  **子能力一：南向接口：EDPA直接调用versatile工作流**

高码智能体可直接拉起子工作流，打破智能体依赖中间控制器的局限。高码智能体可对接控制器与低码工作流两种后端。该功能让企业已有的工作流资产得到更好的复用，开发者无需编写编排胶水代码，即可实现多工作流的灵活组合与高效协同，显著提升开发效率并降低运维成本。

  **子能力二：北向接口：加入任务标识注入机制，支持客户端精准路由与并发呈现**

  高码智能体在每个工作流在返回数据包后，携带特定的"任务标识"。前端客户端界面接收到返回值后，无需二次解析即可根据任务标识将数据自动流向对应的维度标签页或分析看板，实现精准路由。配合后端并行执行机制，前端可实时、异步地更新不同的 UI 内容，确保分析结果互不干扰、按需展示，极大提升复杂决策场景下的交互体验。

- **业务价值**：

  1. **降低编排复杂度**：打破智能体依赖中间控制器的局限，通过高码智能体定义即可声明多工作流的执行逻辑，开发者无需编写编排胶水代码，显著降低开发门槛与维护成本。
  2. **提升处理吞吐量**：支持多工作流的"直接调起"与"串并联混合执行"，串行阶段确保依赖关系正确，并行阶段充分利用计算资源并发执行独立子流，实现高吞吐量的任务处理能力。
  3. **实现界面级多并发展示**：通过为工作流返回值注入任务标识，前端可根据业务维度（不同功能、不同模块）进行精准的数据分发与渲染，避免多工作流结果混叠，提升复杂决策场景下的交互体验。
  4. **后端解耦与可扩展性**：对接控制器与低码工作流，支持通过配置切换开关动态调整后端类型，覆盖企业现有工作流的使用形式，增强高码智能体的通用性与适配能力，新增后端类型无需修改前端逻辑，具备良好的可扩展性。

## 2. 核心参与者与触发条件

- **参与角色**：
  - 高码智能体工程师：负责智能体逻辑开发与配置管理
  - 实施工程师：配置后端参数与部署服务
  - 低码工作流工程师：负责工作流设计与发布
  - 前端客户端界面工程师：负责界面渲染与事件处理

- **触发条件**：
  - 用户在前端界面发起业务请求（如"查询企业信息"、"生成尽调报告"）
  - 前端通过 API 调用高码智能体服务
  - 高码智能体解析请求中的 `intent` 字段，触发工作流路由逻辑

- **用例间依赖关系**：
  ```
  UC-EDPA-GH-001 → UC-EDPA-GH-002 → UC-EDPA-GH-003
  (多工作流路由配置) → (Skill复用) → (事件封装拆封)
  ```

## 3. 标准流程用例

### 用例 UC-EDPA-GH-001：高码智能体适配多工作流接口定义

> **关联需求**：REQ-EDPA-GH-001、REQ-EDPA-GH-002

- **前置条件**：
  1. 已部署 OpenJiuwen 运行时环境，高码智能体与适配服务正常运行；
  2. 高码智能体与低码工作流服务之间通信链路已建立；
  3. 测试数据准备：
     - 合法 workflow_id：`cec344fb-0160-4d29-bec4-f54a53a514ae`
     - 合法 intent：`企业信息查询`
     - 低码工作流 URL：`http://122.223.11.130:443/v1/mock_project_id/workflows/cec344fb-0160-4d29-bec4-f54a53a514ae/conversations/{conversation_id}?workspace_id=10`

- **输入参数**：
  1. **业务请求数据**：包含会话标识、业务参数等；
  2. **路由配置**：指定目标工作流标识（workflow_id + intent）与低码工作流 URL。

- **执行步骤**：
  1. 实施工程师配置低码工作流配置文件，包含每个低码工作流的 `workflow_id`、`intent` 与完整 URL 的映射关系。yaml配置信息参考如下：
     ```yaml
     workflow_routes:
       - workflow_id: "cec344fb-0160-4d29-bec4-f54a53a514ae"
         intent: "企业信息查询"
         url: "http://122.223.11.130:443/v1/mock_project_id/workflows/cec344fb-0160-4d29-bec4-f54a53a514ae/conversations/{conversation_id}?workspace_id=10"
     ```
  2. 高码智能体接收业务请求，根据请求中的 `workflow_id`、`intent` 在配置文件中匹配目标低码工作流 URL；
  3. 高码智能体将请求路由到对应的低码工作流，建立流式连接；
  4. 低码工作流返回执行结果，高码智能体透传业务数据给前端；
  5. 低码工作流执行完成后，返回任务完成标识给高码智能体。

- **后置清理**：
  1. 关闭与低码工作流的 SSE 连接；
  2. 清理临时会话数据；
  3. 重置测试配置。

- **与控制器的区别**：

  | 维度 | 控制器 | 低码工作流 |
  |------|-----------|-----------|
  | URL 配置 | 仅需配置一个控制器 URL | 需为每个工作流单独配置 URL |
  | 路由方式 | 单一路由，请求直接发送到控制器 | 多路由，通过 workflow_id + intent 匹配目标工作流 |
  | 多后端场景 | 无需额外配置，控制器内部处理分发 | 需有低码工作流配置文件，管理多个工作流 URL |
  | 适用场景 | 复杂多轮交互、统一管控 | 独立任务、灵活组合 |

- **预期输出/结果**：
  1. 高码智能体能够通过配置文件调用多个低码工作流的路由信息；
  2. 同一请求根据 `workflow_id` 和 `intent` 正确路由到对应的低码工作流；
  3. 低码工作流的返回值能够透传回前端界面，并且前端界面可以识别不同工作流返回值；
  4. 新增或修改低码工作流时，仅需更新配置文件，无需修改高码智能体代码；
  5. 与控制器的配置方式明确区分，满足不同业务场景的部署需求。

### 用例 UC-EDPA-GH-002：统一由配置文件管理控制器与低码工作流，实现 Skill 复用

> **关联需求**：REQ-EDPA-GH-003
> **前置依赖**：UC-EDPA-GH-001

- **前置条件**：
  1. 高码智能体已部署，支持通过统一 YAML 配置文件管理后端；
  2. 同一份 Skill 代码需在控制器和低码工作流两种场景下可复用；
  3. 同一份高码智能体代码需部署到多个局点，各局点可能对接不同类型的后端；
  4. 测试数据准备：
     - 控制器 URL：`http://122.223.11.130:8080/v1/mock_project_id/agent-manager/workflows/{workflow_id}/conversations/{conversation_id}`

     - workflow_id：`cec344fb-0160-4d29-bec4-f54a53a514ae`、`abc12345-xxxx-xxxx-xxxx-xxxxxxxxxxxx`
     - intent：`企业信息查询`、`尽调报告生成`
     - url： "http://122.223.11.130:443/v1/mock_project_id/workflows/abc12345-xxxx-xxxx-xxxx-xxxxxxxxxxxx/conversations/{conversation_id}?workspace_id=10"

- **输入参数**：
  1. **统一 YAML 配置文件**：包含控制器 URL（可选）和低码工作流路由表（可选）；

- **执行步骤**：
  1. 实施工程师配置统一的 YAML 文件，支持同时配置控制器 URL 和低码工作流路由表。yaml配置信息参考如下：
     ```yaml
     # 控制器配置（可选）
     controller_url: "http://122.223.11.130:8080/v1/mock_project_id/agent-manager/workflows/{workflow_id}/conversations/{conversation_id}"

     # 低码工作流路由表（可选） 
     workflow_routes:
       - workflow_id: "cec344fb-0160-4d29-bec4-f54a53a514ae"
         intent: "企业信息查询"
         url: "http://122.223.11.130:443/v1/mock_project_id/workflows/cec344fb-0160-4d29-bec4-f54a53a514ae/conversations/{conversation_id}?workspace_id=10"
       - workflow_id: "abc12345-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
         intent: "尽调报告生成"
         url: "http://122.223.11.130:443/v1/mock_project_id/workflows/abc12345-xxxx-xxxx-xxxx-xxxxxxxxxxxx/conversations/{conversation_id}?workspace_id=10"
     ```
  2. 高码智能体启动时加载统一 YAML 配置文件；
  3. 高码智能体接收业务请求，提取请求中的 `intent` 信息；
  4. 高码智能体根据 `intent` 在 `workflow_routes` 中进行 YAML 映射查找：
     - 若找到匹配的 `workflow_id`：走**低码工作流模式**，路由到对应的低码工作流 URL；
     - 若未找到匹配的 `workflow_id`：走**高码（控制器）模式**，路由到 `controller_url`；
  5. 同一份 Skill 代码无需修改，通过 YAML 配置即可自动适配不同后端类型。

- **后置清理**：
  1. 关闭所有后端连接；
  2. 清理路由缓存；
  3. 重置配置文件到默认状态。

- **预期输出/结果**：
  1. 同一份高码智能体代码支持多局点部署，各局点可通过统一 YAML 文件独立配置后端；
  2. Skill 在控制器和低码工作流两种场景下可复用，无需修改业务代码；
  3. 高码智能体根据请求中的 `intent` 自动在 YAML 配置中映射 `workflow_id`，实现后端类型的自动选择；
  4. 若 `intent` 匹配到 `workflow_id`，自动路由到低码工作流；未匹配到则路由到控制器；
  5. 路由逻辑对上层业务逻辑透明，业务代码无需感知后端类型差异。

### 用例 UC-EDPA-GH-003：子任务生命周期事件推送与层级拆封

> **关联需求**：REQ-EDPA-GH-004、REQ-EDPA-GH-005
> **前置依赖**：UC-EDPA-GH-001、UC-EDPA-GH-002

- **前置条件**：
  1. 高码智能体已启动，并监听子任务生命周期事件；
  2. 前端已建立 SSE 连接，可接收事件推送；
  3. 后端低码工作流服务通信正常；
  4. 子 Agent 支持 `workflow` 信封封装，主 Agent 支持 `Sub_task` 信封封装；
  5. 测试数据准备：
     - task_id：`task_id-001`、`task_id-002`，由runtime动态分配；
     - workflow_id：`cec344fb-0160-4d29-bec4-f54a53a514ae`
     - conversation_id：`conver_original`，由前端输入，用于标识当前会话；

- **输入参数**：
  1. **业务请求数据**：包含会话标识、业务参数等；
  2. **路由配置**：指定目标工作流标识（workflow_id + intent）与低码工作流 URL。

- **执行步骤**：
  1. 高码智能体解析用户请求，拆分为多个子任务并分配唯一 `task_id`，同时记录每个子任务对应的 `workflow_id`；
     - `task_id`：用于路由到对应的子任务界面区域；
     - `workflow_id`：用于在子任务界面区域内确定工作流的展示位置；
  2. 高码智能体推送 `sub_task` 事件给前端，前端建立 `task_id` 与 `task_message` 的映射关系,映射示例参考如下；
       ```json
     {
       "success": true,
       "agent_id": "xx",
       "conversation_id": "xx",
       "output": "",
       "error": "",
       "execution_time": 0.065,
       "custom_rsp_data": {
         "data": {"event_status": "start","task_id": "123456", "task_message": "小米企业"},
         "event": "sub_task"
       }
     }

  3. 高码智能体将子任务路由到对应的低码工作流执行；
  4. **子流程侧包装**：工作流返回事件时，子 Agent 将其封装为 `workflow` 信封：
     ```json
     {
       "event": "workflow",
       "workflow_id": "cec344fb-0160-4d29-bec4-f54a53a514ae",
       "event_status": "report"
       "data": {低码返回值
       }
     }
     ```
  5. **主流程侧包装**：高码智能体收到子 Agent 事件后，随主 Agent 事件上报（`start` 开始拆分，`report` 消息上报，`end` 结束）：
     ```json
     {
       "success": true,
       "agent_id": "main_agent",
       "conversation_id": "conver_original",
       "custom_rsp_data": {
         "event": "sub_task",
         "data": {
           "task_id": "task-001",
           "event_status": "report",
           "data": {
             "event": "workflow",
             "event_status": "report",
             "workflow_id": "cec344fb-0160-4d29-bec4-f54a53a514ae",
             "data": {低码返回值}
           }
         }
       }
     }
     ```
  6. **应用侧拆封**：前端按层级依次拆封：
     - 第一层：识别主 Agent 事件，提取 `sub_task` 事件；
     - 第二层：拆封提取 `task_id` ;
     - 第三层：拆封 `workflow`，提取 `workflow_id` 和最终业务数据；
  7. 前端根据 `task_id` 和 `workflow_id` 进行两级路由，客户端web界面可根据workflow_id映射到对应的子任务界面区域进行渲染。

- **后置清理**：
  1. 关闭 SSE 连接；
  2. 清理前端事件监听；
  3. 销毁子任务界面区域；
  4. 释放相关资源。

- **预期输出/结果**：
  1. 工作流事件在子流程侧封装为 `workflow`，随子 Agent 事件上报；
  2. 子 Agent 事件在主流程侧封装为 `sub_task`，随主 Agent 事件上报给应用层；
  3. 应用侧按"主 Agent → 子 Agent → workflow"层级依次拆封，完整还原原始事件内容；
  4. 拆封后获取 `task_id` 和 `workflow_id`，实现两级路由：
     - 根据 `task_id` 路由到子任务界面区域；
     - 根据 `workflow_id` 在区域内确定展示位置；
  5. 并行场景下，多个工作流事件独立封装、并发推送，前端分别拆封并精准路由到对应位置。

### 用例 UC-EDPA-GH-007：conversation_id拆分处理（并行请求场景）

> **关联需求**：REQ-EDPA-GH-005

- **前置条件**：
  1. 高码智能体已启动；
  2. 低码工作流不支持同一 conversation_id 并行请求；
  3. 测试数据准备：
     - 原始 conversation_id：`conv-original`
     - 多个并行子任务

- **输入参数**：
  1. **业务请求**：包含多个并行子任务

- **执行步骤**：
  1. 高码智能体解析请求，拆分为多个并行子任务；
  2. 为每个子任务生成独立的 conversation_id（格式：`{原始conversation_id}_{task_id}`）；
  3. 分别路由每个子任务到对应的低码工作流；
  4. 工作流返回结果后，高码智能体映射回原始 conversation_id；
  5. 统一封装后上报给前端；

- **后置清理**：
  1. 清理拆分后的临时 conversation_id；
  2. 合并会话状态；
  3. 释放资源。

- **预期输出/结果**：
  1. 每个子任务获得独立的 conversation_id；
  2. 并行请求正常执行，互不干扰；
  3. 前端收到统一的响应，conversation_id 为原始值；

> **关联需求**：REQ-EDPA-GH-001、REQ-EDPA-GH-002、REQ-EDPA-GH-003

- **输入参数**：
  1. **边界值 YAML 配置文件**：包含各类边界值参数组合

- **执行步骤**：

  **场景一：workflow_routes 条数边界**

  1. 配置 `workflow_routes` 为空（0条），仅配置 `controller_url`；
  2. 高码智能体启动加载配置，所有请求路由到控制器；
  3. 配置 `workflow_routes` 为1条，验证单条路由正常工作；
  4. 配置 `workflow_routes` 为N条（如50条），验证多条路由加载不溢出、不丢路由项；
  5. 发送不同 intent 的请求，验证每条路由均能正确匹配。

  **场景二：intent 字符串边界**

  1. 配置 `intent` 为极长字符串（如1000个字符）；
  2. 高码智能体启动加载配置，验证配置解析不崩溃；
  3. 发送包含极长 intent 的请求，验证路由匹配行为；
  4. 配置 `intent` 为含特殊字符的字符串（如 `<script>alert(1)</script>`、`'; DROP TABLE--`、`🎉🔥`）；
  5. 高码智能体启动加载配置，验证不发生注入、不做HTML渲染，特殊字符做转义或校验拒绝。

  **场景三：workflow_id 格式边界**

  1. 配置 `workflow_id` 为非 UUID 格式（如 `abc`、`123-456`、纯数字 `99999`）；
  2. 高码智能体启动加载配置，验证格式校验逻辑；
  3. 配置 `workflow_id` 为空字符串；
  4. 高码智能体启动加载配置，验证空值校验逻辑。

  **场景四：URL 长度与协议边界**

  1. 配置 `url` 为超长 URL（如2000+字符）；
  2. 高码智能体启动加载配置，验证配置解析不溢出；
  3. 配置 `url` 为非法协议（如 `ftp://127.0.0.1/workflow`、`javascript:alert(1)`）；
  4. 高码智能体启动加载配置，验证协议校验逻辑；
  5. 配置 `url` 为格式非法的字符串（如 `not-a-url`、`://missing-host`）；
  6. 高码智能体启动加载配置，验证URL格式校验逻辑。

  **场景五：controller_url 与 workflow_routes 同时为空**

  1. 配置文件中 `controller_url` 为空且 `workflow_routes` 为空；
  2. 高码智能体启动加载配置；
  3. 发送业务请求，验证系统行为。

- **后置清理**：
  1. 恢复配置文件到合法状态；
  2. 清理错误日志；
  3. 重启高码智能体。

- **预期输出/结果**：

  | controller_url 与 workflow_routes 同时为空 | 启动报错或启动后请求返回明确错误，提示至少配置一种后端 |

## 5. 依赖项

- **依赖说明**：
  1. **高码智能体服务**：需部署 OpenJiuwen 运行时环境，支持子任务管理；
  2. **后端服务**：控制器服务或低码工作流服务，需部署且网络可达，支持 SSE 流式返回；
  3. **统一 YAML 配置文件**：支持配置 `controller_url`（可选）和 `workflow_routes`（可选），Skill 在两种场景下可复用；
  4. **后端类型智能路由支持**：高码智能体根据请求中的 `intent` 在 YAML 配置中自动映射 `workflow_id`，支持不同类型请求的灵活路由；
  5. **前端两级路由映射**：前端需注册 `task_id` 与界面区域的映射关系，以及 `workflow_id` 与客户端子界面内展示位置的映射关系，支持精准路由渲染；
  6. **conversation_id 改造支持**：高码智能体支持为每个子任务生成独立的 `conversation_id`（格式：`{原始conversation_id}_{task_id}`），解决低码工作流不支持同一会话承载多个并行请求的问题；
