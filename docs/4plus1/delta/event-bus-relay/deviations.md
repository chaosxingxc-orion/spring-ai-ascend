This is real lifecycle wiring (`@PostConstruct` / `InitializingBean` / a `SmartLifecycle`), not just bean construction.

## G5-E — two-hop IT surfaced + fixed 3 substrate bugs (the boot-correctness deferred from G5-B)

G5-E (`RealBrokerTwoHopRelayIntegrationTest`, env-guarded, direct construction + real JdbcForwardingInbox/Outbox + embedded-postgres + real broker) is the boot-verification deferred from G5-B (compile-verify was the floor; the deviations above said "boot-correctness deferred to G5-E"). It surfaced three bugs the unit tests (InMemoryOutbox + FakeInbox) hid — each a place the G5-A worker's governance assumed something the real JDBC substrate didn't provide. All three are fixed + the IT is 4/4 green (broker env); full suite 434 green / 14 skip / 0 fail (no regression).

1. **Response relay couldn't relay responses (bug #1).** `EventBusRelayWorker` was request-only: `isForwardRequestType` returned false for `INVOCATION_ACCEPTED/RESPONSE/TERMINAL` (governance-1 skip) AND governance-2 required a `BrokerControlDescriptor` (responses carry `taskId=…;status=…` tokens, not a descriptor → decode throws → rejectPoison). So G5-B's `responseRelayWorker` (resp_in→resp_out) would skip/reject every response → the gateway never saw `resp_out` → `acceptWindow` DEFERRED. L2 §4.1 mandates the response relay re-publish responses with governance. **Fix:** the response carries a descriptor symmetric to the request (control fields recovered from it; `taskId`/`status` ride as extra tokens the gateway reads via `BrokerControlDescriptor.token`), and `EventBusRelayWorker` takes a `Set<AgentBusEventType> relayableTypes` param (`FORWARD_REQUEST_TYPES` / `RESPONSE_TYPES`) — the forward + response relays reuse the SAME governance (decode + correlation-match + inbox-dedup + re-publish + audit); only the relayable-types set differs. The "skip descriptor decode" the user initially approved was infeasible: `ForwardingEnvelope` requires non-blank `traceId`/`idempotencyKey`/`capability`/`routeHandle` that `BrokerInboundMessage` doesn't carry — only a descriptor provides them. Reusing forward governance is cleaner + more faithful to L2 §4.1 ("Inbox dedup + correlation match") than the approved branching.

2. **`markRejected` threw without a prior `receive` (bug #2).** `rejectPoison` (governance-2 decode-fail / governance-3 corrId-mismatch) calls `inbox.markRejected` BEFORE `inbox.receive` (those governances fire before governance-4). The real `JdbcForwardingInbox.markRejected` ran `UPDATE … WHERE status='RECEIVED'` (guarded terminal mutation) → 0 rows → `IllegalStateException` (no prior RECEIVED row). The unit test hid it (`FakeInbox.markRejected` doesn't require a prior row). **Fix:** `JdbcForwardingInbox.markRejected` is an **upsert** (INSERT REJECTED if no prior row — the poison-audit row; UPDATE RECEIVED→REJECTED if present; idempotent on already-terminal via the `WHERE status='RECEIVED'` guard on the conflict branch). `markConsumed` stays the guarded `mutate` (a consume always follows a receive). Mirrored in `InMemoryForwardingInbox`. Contained — only `rejectPoison` calls `markRejected`-without-`receive`.

3. **`JdbcForwardingOutbox` didn't persist `correlationId`/`eventType` (bug #3).** The V1 outbox schema predates FEAT-013's envelope extensions; `ForwardingSqlCodec.mapOutbox` hardcoded `correlationId=null`/`eventType=null` with the comment "Add a V3 migration + column read when FEAT-013 wires JDBC." So the gateway's `dispatchRequest` produce (outbox→claimDue→`RocketMqBrokerForwardingRelay.buildMessage`) stamped no `correlationId`/`eventType` user-properties (`if (record.correlationId() != null)`) → the forward relay's correlation-match (`null ≠ descriptor`) rejected every gateway-produced hop1, AND the gateway's `acceptWindow` (classify by NATIVE `eventType`) would yield UNKNOWN. **Fix:** V3 migration adds `correlation_id` + `event_type` (nullable) to `agent_bus_forwarding_outbox`; `JdbcForwardingOutbox.enqueue` persists them; `ForwardingSqlCodec.mapOutbox` reads them (`decodeEventType`). Anticipated by the V1 + codec comments — this IS the FEAT-013 JDBC wiring.

**Happy-path uses `sendHop1` (directProducer) for hop1.** The gateway's `dispatchRequest` produce is verified separately (`BrokerForwardingRelayPort.produce` returns ACCEPTED — observed during G5-E; the JDBC outbox enqueue/claimDue is verified by `ForwardingJdbcIntegrationTest`). A broker consumer-group queue-assignment quirk kept the shared `forwardRelayConsumer` (LitePull, new group, drained at `@BeforeEach`) from polling `gatewayProducer`'s hop1 in the test window, while `directProducer`'s messages ARE polled (despite both on `ascend_bus_invocation_req`). So the happy-path drives the relay path + `acceptWindow` via `sendHop1` (which the consumer polls), bypassing the consumer quirk. The 3 governance tests (dedup-on-replay via real `ON CONFLICT`, cross-tenant broker-side bySql, corr-mismatch→REJECTED-audit) verify the forward relay's core governance against the real broker + real Postgres.

**Test isolation.** The broker does NOT reliably persist `DefaultLitePullConsumer` offsets across `mvn` runs NOR start a new group at `CONSUME_FROM_LAST_OFFSET` — so prior runs' (slice-3 + this IT) unconsumed messages redeliver + pollute. Fixed with run-unique consumer-group suffixes (fresh groups each run) + a `@BeforeEach` `drainAll` (test-only, `RocketMqBrokerForwardingConsumer.drainAll` polls+acks the raw `MessageExt` without `toInbound`, clearing even malformed leftovers that would NPE in `toInbound`).

### #1 `DeliveryFilter.matches` altitude — ACCEPT (defer)
The finding proposed adding `DeliveryFilter.matches(Function<String,String>)` + `BrokerMessageHeaders.property(String)` to collapse the `InMemoryBroker.headerProperty` closed switch + the duplicated matching loop. **Deferred, not landed:**
- The closed switch + matching live only in `InMemoryBroker` / `InMemoryBrokerConsumer` (`src/test` — a test double), not production. The duplication motive is already gone: slice-3 (`201f119c`) deleted `ResponseSideConsumer`, leaving `InMemoryBrokerConsumer.matches` as the sole copy.
- No production consumer needs `DeliveryFilter.matches` — the real path filters broker-side via `MessageSelector.bySql(sql92Expression(filter))`; the only client-side match is the test double + `GatewayRuntimeService.acceptWindow`'s own tenant/correlationId logic (not via `DeliveryFilter`).
- The "drops a message a real broker would deliver" risk is latent-only: every filter in use keys on `tenantId` / `targetServiceId` (inside the switch's set); no filter keys outside the set.
- Adding a method to the `DeliveryFilter` SPI record is a contract change that warrants its own decision (broker-filtering decision packet §3 / D3), not a silent CLOSED-loop add.

**Trigger to land:** introduce `DeliveryFilter.matches` + `BrokerMessageHeaders.property(String)` when a second broker adapter that degrades to client-side filtering (D7 — Kafka / Redis Streams) is introduced, or when a production consumer needs client-side matching. Until then it is premature abstraction (flexibility with no consumer).

### #3 D13 forward-relay tenant-only filter + multi-tenant subscribe — ACCEPT
**(a) Forward-relay tenant-only filter is correct (not a D13 violation).** The relay is the governance intermediary for its tenant, so it consumes every in-tenant message on its hop-in topic — reqs are targeted at runtimes, responses at callers, neither at the relay itself; a `targetServiceId` pin would starve it. The tenant-only `DeliveryFilter(Map.of("tenantId", tenant))` IS the L2 §4.5 broker-layer tenant check (poll with `tenantId`; broker does not deliver header-tenantId ≠ poll-tenantId) and the §4.1 sequence (`consumer=event-bus, tenant`). D13 (targetServiceId-only) was gateway-response-consumer-specific and is already resolved by G5-B (`GatewayRuntimeConfiguration.gatewayResponseSubscription` uses `DeliveryFilter(Map.of("targetServiceId", gateway))`). Recorded in the `EventBusRelayConfiguration` class javadoc.

**(b) Multi-tenant subscribe is a deferred refinement, not a defect.** `agent-bus.tenant` (`AgentBusBrokerProperties`, default `default`) is the single-tenant-per-deployment subscribe scope — a valid deployment model (one event-bus process per tenant). A multi-tenant relay subscribe (one process serving several tenants) is an explicit future refinement, already FIXME'd at `EventBusRelayConfiguration.relaySubscriptions` + the `AgentBusBrokerProperties.tenant` javadoc. Land when a multi-tenant relay requirement materializes. The default is fail-safe (a misconfigured tenant processes only its own messages — no cross-tenant leak).
